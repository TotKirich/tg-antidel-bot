# Безопасность и приватность

Этот документ описывает текущую реализацию и границы защиты. Он не является заключением независимого аудита и не обещает отсутствие уязвимостей.

## Модель доступа

Сервис предназначен для одного владельца на доверенном сервере. Пользовательская Telegram-сессия получает входящие сообщения и доступные сторис, сохраняет копии и отправляет архив в Telegram. Бот уведомлений использует отдельный токен. Используйте собственный аккаунт и учитывайте приватность участников переписок.

Администратор и получатель привязываются к числовому ID вошедшего аккаунта. Команды управления принимаются только в личном чате этого ID; username не используется как право доступа. Существующую папку данных нельзя молча перепривязать к другому владельцу. Root, владелец файлов и пользователи с доступом к Docker находятся вне этой границы защиты: они могут прочитать секреты сервиса.

## Какие данные сохраняются

- config.json: API ID/hash, токен бота, ID владельца и настройки.
- Telegram-сессия: ключ авторизации и служебный кеш клиента. Относитесь к ней как к доступу к аккаунту.
- SQLite: полученные тексты/подписи, имена и ID, сведения о чатах, история правок, сторис, очереди, привязки архива и ограниченные бинарные метаданные Telegram.
- media/: скачанные фото, видео, аудио и документы.
- Снимок имён контактов: ID, имена, username без отдельного сохранения телефонов в этой таблице. Исходные сообщения, карточки контактов, файлы и кеш Telegram могут сами содержать телефоны и другие личные сведения.
- Журналы и резервные копии: диагностические сведения и, для резервной копии, содержимое исходных приватных файлов.

Одноразовый код и пароль 2FA приложение не записывает в конфигурацию, БД или собственные сообщения журналов. Ключи приложения и токен сохраняются для фоновой работы, но не возвращаются в ответы формы и не подставляются в поля. Пустое поле при перенастройке означает сохранение текущего значения.

Локальная SQLite, файлы и конфигурация **не зашифрованы приложением**. Ограниченные права файлов не заменяют шифрование диска или защиту сервера. Архивные копии отправляются на серверы Telegram; закрытая группа не является исключительно локальным хранилищем. Приглашённые вами участники группы смогут видеть доступную им историю.

## Временный веб-вход

API требует случайный временный bearer-ключ из полной ссылки и отклоняет чужой Origin, если он передан. Ключ находится после `#`, убирается из адресной строки и сохраняется в sessionStorage вкладки до завершения. Он не является API hash или токеном бота, но позволяет управлять текущим процессом настройки: не делитесь им.

Форма не заполняет сохранённые секреты, использует no-store и защитные заголовки; access log отключён. QR генерируется локально и выдаётся через защищённый endpoint, без внешнего генератора. После завершения listener закрывается и файл ссылки удаляется. Пока настройка не закончена, listener остаётся открыт; повторный вход/настройка могут открыть его снова.

Встроенный HTTP **не шифрует ввод**. Launcher может выбрать частный LAN-адрес автоматически. Для удалённого или недоверенного сегмента задайте loopback и SSH-туннель по [инструкции](DEPLOYMENT.md). Не открывайте порт в Интернет. Запрет bind на 0.0.0.0 не является межсетевым экраном.

## Готовые образы и приватная установка

Workflow публикации запускается только вручную и только в private-репозитории. Для него используются временный GITHUB_TOKEN и минимальные права contents:read/packages:write; постоянный PAT в Actions не добавляется. Перед публикацией и после push проверяется доступность метаданных пакета и допустимая visibility (private/public). Для публичной установки владелец отдельно открывает только проверенный runtime-пакет; приватный preview остаётся закрытым. Bootstrap использует последнюю успешную сборку и закрепляет локальный образ по digest.

Для private-установки classic PAT нужен для GitHub и GHCR. Он вводится скрыто, используется в окружении установщика, не записывается в проект или app config. Временный Docker config с авторизацией создаётся в /dev/shm и очищается после pull/при выходе. Root и владелец процесса по-прежнему могут прочитать память/окружение: это не граница защиты от администратора хоста. Небольшой bootstrap скачивает и выполняет служебные shell-файлы проекта по конкретному commit через HTTPS; проверяйте доверие к репозиторию.

## Установка Docker

При отсутствии Docker start.sh автоматически запускает установку системных пакетов из официального подписанного apt-репозитория на поддерживаемой Ubuntu/Debian. Это привилегированное изменение ОС через root/sudo, без отдельного подтверждения установщика. Код не удаляет конфликтующие runtime и не настраивает TCP-доступ daemon или членство в группе docker. Проверяйте исходники перед запуском с sudo.

## Защита процесса и данных

Docker-образ запускает guard по умолчанию, launcher задаёт UID/GID текущего пользователя. Root-filesystem контейнера read-only, capabilities сняты, включён no-new-privileges. Каталог /data остаётся доступным для записи; Linux host networking не обеспечивает сетевую изоляцию. Не запускайте launcher от root, если это не необходимо вашей среде.

Конфигурация обновляется атомарно с межпроцессной блокировкой; используются закрытая umask и приватные режимы новых файлов. Секреты исключены из контекста Docker по разрешающему списку. SQLite/WAL, постоянные очереди и supervisor снижают риск потери работы, но не являются гарантией доставки или защитой от чтения диска.

Срок хранения и очистка относятся к локальным данным. Уже отправленные сообщения и файлы в Telegram автоматически не удаляются вместе с локальными копиями. Резервные сессии и внешние резервные копии требуют отдельного управления сроком хранения.

## Перед публикацией и при утечке

Публикуйте только чистую сборку, проверьте staged diff и не добавляйте data, config.json, сессии, БД, журналы, полные ссылки входа или дампы переписки. `.gitignore` не очищает уже существующую Git-историю.

Если секрет уже был опубликован, новая чистая сборка не отзывает его и не удаляет старые копии. Отзовите токен через BotFather или завершите затронутую Telegram-сессию в настройках устройств; порядок дальнейшей очистки истории описан в [GitHub Docs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository). Не помещайте значения секретов в issue или команды, попадающие в shell history.

## Сообщить об уязвимости

Если владелец репозитория включил GitHub Private vulnerability reporting, используйте Security → Report a vulnerability. Иначе создайте issue только с просьбой о приватном канале связи, без эксплуатационных деталей и личных данных.

Для приватного отчёта достаточно версии/коммита, затронутого компонента, сценария воспроизведения на вымышленных данных, ожидаемого и фактического результата. Не прикладывайте действующие токены, Telegram-сессии или базу переписки. Чувствительные материалы не публикуйте в обычных issues.

Исправления проверяются на текущем исходном коде; формального SLA и гарантированного сопровождения старых сборок нет. Известные ошибки тем и медиазаданий перечислены в DEPLOYMENT.md и сами по себе не доказывают нарушение конфиденциальности.
